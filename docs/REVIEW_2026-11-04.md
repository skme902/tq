## High

### H1. More than `GetTasksBatchSize` outstanding leases stall the backlog (verified)

**Status: fixed** in c847ed0 (branch `feat/review-fixes`). Leased tasks count in `leasedTasks`, not `loadedTasks`. Test `TestHeldLeasesDoNotStallBacklog` fails on `6e4b017`. Parity: `run_probes.sh` "Held leases" (PARITY_REPORT §2.6).

- **Where:** `internal/matching/fair_task_reader.go:230-239` (`shouldReadMoreLocked`) and `:208-216`; `delivery.go`
  header comment.
- **What happens:** A leased backlog task stays "loaded, not acked" for the whole lease, so it keeps counting toward
  `loadedTasks`. A new read starts only when `loadedTasks <= GetTasksReloadAt`, and a read loads at most
  `GetTasksBatchSize - loadedTasks` tasks. As a result, each subqueue can have at most `GetTasksBatchSize` leases in
  flight (1000 by default). Once consumers hold more than `ReloadAt` leases, polls return "no tasks" even though the
  backlog is deep.
- **Probe:** batch size 50, `ReloadAt` 10, 200 tasks added, then polls that hold each lease. Poll 51 returned "no tasks".
  Status at that point: `LoadedTasks:50, Backlog:200, AckLevel <0,0>`.
- **Upstream:** no equivalent problem. Upstream acks as soon as RecordTaskStarted returns
  (`service/matching/fair_task_reader.go` `completeTask`), so `loadedTasks` counts only tasks that are waiting in the
  matcher. PARITY_REPORT §3 item 1 describes the lease model but not this capacity limit.
- **Fix:** Track leased tasks separately (for example a `leasedTasks` counter, or mark the btree entry as leased).
  Remove them from `loadedTasks` when they are handed out but keep them pinning the ack level. Base
  `shouldReadMoreLocked` and the read size only on unleased tasks. Optionally add `MaxOutstandingLeases` as a deliberate
  backpressure setting. Document the limit either way. Effort: M (reader accounting plus tests; must be done together
  with H2).

### H2. A leased task is delivered again while its lease is still held (verified)

**Status: fixed** in c847ed0. Trims skip leased entries; chopped leased tasks are tracked in `leasedEvicted`. Test `TestHeldLeaseNotRedeliveredAfterTrim` fails on `6e4b017`. README at-least-once text corrected.

- **Where:** `fair_task_reader.go:473-520` (`mergeTasksLocked`, trim steps 2 and 4) together with `:156-167`.
- **What happens:** When a write or read pushes the in-memory set over `GetTasksBatchSize`, the highest-level entries
  are chopped. A chopped entry that is currently leased loses its `outstandingTasks` slot, which decrements
  `loadedTasks` and lowers `readLevel` below it. The next read gets the same row from the store again, and nothing marks
  it as leased (`evictedAcks` is set only after a successful Ack). So the task goes back to the matcher and another
  poller receives it while the first lease is still live. If the first holder Acks later, the ack lands in
  `evictedAcks`. If the second holder Acks first, the first holder's Ack also succeeds. Either way the task has been
  processed twice.
- **Probe:** batch size 50, `ReloadAt` 10. Add 5 tasks with key A at weight 0.01; these get high pass values. Poll and
  hold all 5. Add 60 tasks with key B at weight 1; these have lower passes, so the trim chops the A tasks. Poll and ack
  the B tasks. Result: tasks 1–5 were each delivered a second time while their first lease was held.
- **Why it matters:** The README (`At-least-once delivery`) says duplicates happen "after a crash or a queue reload".
  This one happens in steady state on a single engine, under ordinary fairness skew. PARITY_REPORT §2.1 shows 0
  duplicates only because the harness acks immediately and never holds leases.
- **Upstream:** the same trim exists (`fair_task_reader.go` `mergeTasksLocked`), but there a chopped task is either still
  in the matcher (`setEvicted` removes it) or already started and deduped by history. tq has no history dedupe, so the
  lease model adds a case upstream never has.
- **Fix:** Never chop leased entries. During the trim scan, skip leased entries as well as acked ones, so they stay in
  `outstandingTasks` and keep `readLevel` above them. Alternatively, keep a `leased` set keyed by level that the merge
  checks the same way it checks `evictedAcks`. Add a regression test based on the probe below. Effort: M; fix together
  with H1.

## Medium

### M1. A sync-matched task can be lost during `Engine.Stop` (suspected)

**Status: fixed** in 18f4e94; L6 (f87e3f4) extended it to all leases. Reproduced: `TestStopRaceSyncMatchNotLost` drives the interleaving with a Stop test hook and fails with the `syncLeasesClosed` check disabled.

- **Where:** `engine.go:119-131` and `:332-355`.
- **What happens:** Stop takes a snapshot of `syncLeases` and then stops the partitions. A `PollTask` or `AddTask` that
  got its partition manager before `stopped` was set can still sync-match after the snapshot. `newDelivery` adds that
  lease to `syncLeases`, the `AddTask` caller is told the task was matched, and the lease is never re-spooled by Stop. If
  the lease later expires or is Nacked, `respoolSyncTaskLocked(shuttingDown=false)` finds `pm.tqCtx` cancelled. It then
  calls `getTaskQueuePartitionManager`, which returns `ErrEngineStopped`, and the task is logged as lost.
- **Upstream:** no counterpart; this comes from the lease addition (§3 item 1).
- **Fix:** Have `newDelivery` check `e.stopped` while holding `syncLeasesLock` and re-spool immediately when the engine is
  stopped. Alternatively, drain new syncLeases in a loop until the set stays empty after all partitions have stopped.
  Effort: S.

### M2. `ExtendLease` can report success on a lease that then expires (suspected)

**Status: fixed** in 6d13500. Reproduced: `TestExtendLeaseBeatsStaleExpiry` (fake clock) fails without the deadline re-check.

- **Where:** `delivery.go:128-146`.
- **What happens:** If the timer has already fired and `expire` is blocked on `d.mu` inside `settle()`,
  `ExtendLease` takes the lock, sees `settled == false`, resets the timer, and returns nil. Then `expire` settles the
  lease and redelivers the task. The caller believes it still owns the task. The next Ack does return `ErrLeaseLost`,
  but by then the task may already be running somewhere else.
- **Fix:** In `expire`, after taking `d.mu`, re-arm when `now < d.deadline` (the extension won) and settle only when the
  deadline has passed. Also reject `dur <= 0`. Effort: S.

### M3. Start after Stop can leak a partition (suspected)

**Status: fixed** in 3765c79. Reproduced: `TestPartitionStartAfterStopIsNoop` fails without the fix.

- **Where:** `engine.go:146-194` (Start runs outside `partitionsLock`) and `physical_task_queue_manager.go:148-172`
  (Start/Stop CAS).
- **What happens:** `getTaskQueuePartitionManager` publishes `newPM` and then calls `newPM.Start()` after releasing the
  lock. A concurrent `Engine.Stop` or idle unload can remove and Stop the pm in between. If the physical manager's Stop
  CAS (Initialized→Stopped) runs before its Start CAS, Stop does nothing. Start then launches the backlog goroutines, the
  rate-limit watcher and the idle timer on a pm that is no longer in the map.
- **Upstream:** same shape (`matching_engine.go` getTaskQueuePartitionManager), but upstream's physical Start/Stop use
  `common.DaemonStatusInitialized→Started` and Stop checks `Started→Stopped`, so the same window exists there. tq
  additionally starts a config watcher in `rateLimitManager.Start`, which upstream does not have. Low likelihood
  (shutdown only).
- **Fix:** Make Start a no-op once Stop has run (CAS Initialized→Stopped in Stop as well), or Start the pm before
  publishing it. Effort: S.

- **L1. `addErrorRetryPolicy` has no maximum interval (verified by reading).** `fair_task_reader.go:27` sets only
  `Initial: 2s`. Upstream `pri_task_reader.go:63` builds it with `NewExponentialRetryPolicy`, whose default maximum is
  10s (`common/backoff/retrypolicy.go:20`). In tq the backoff in `retryAddAfterError` keeps doubling: about 34 minutes
  by attempt 10, and `time.Duration` overflows at attempt 33. Fix: `Max: 10 * time.Second`. Effort: XS.
  **Fixed** (fdb01f3): `Max: 10s`; `Policy.interval` saturates. Tests `TestAddErrorRetryPolicyCapped`, `TestIntervalSaturatesWithoutMax`.
- **L2. `internal/backoff.ThrottleRetryContext` differs from upstream (verified by reading).** Upstream
  `common/backoff/retry.go:50-100` stops at the ctx deadline, raises the delay for ResourceExhausted errors, and loops

## Upstream behaviors rechecked and found matching

- **Fair task reader:** `mergeTasksLocked` read and write modes, `atEnd` and `readLevel` handling, `advanceAckLevelLocked`, transient-error
  re-add, and the reader backoffs (50ms→10s and 2s→30s). The documented differences (evictedAcks `:156-165`, maybeGC
  `:681-688`, the numToGC floor `:717-725`) are as described in §3.
- **Fair task writer:** pass assignment, dither, rangeID block allocation, and the persistence and forever retry policies.
- `fairness_util`, all config defaults, and long-poll expiration jitter.
- **Backlog manager:** Stop (`fair_backlog_manager.go:117-137` vs upstream `:113-134`) and `periodicSync` (plus the
  documented `maybeGC`). The lock order in `InternalStatus` (subqueueLock → db) is consistent.
- **Priority matcher:** Start and `validateTasksOnRoot` (`pri_matcher.go:123-159` vs upstream `:249-285`), and `Offer`
  (`:175-221` vs `:390-440`). `matcher_data.go` is identical apart from the clock and the removed query path.
- **Rate limiting:** effective-RPS compute, apply, consume and clip, per-key weight scaling, and LRU sizing.
- **db:** `SyncState`, `verifyOwnership`, `updateTaskQueueLocked`, `updateFairAckLevel` and `CreateFairTasks` fencing and
  ConditionFailed → unload.
- **Physical and partition managers:** Start/Stop order (rate limiter → user data → default queue; Stop in reverse).
- **SQL stores:** queue lock before task writes, `FOR UPDATE` on Postgres, `BEGIN IMMEDIATE` on SQLite, range delete
  with LIMIT (ctid variant on Postgres), and the documented upsert on duplicate insert.
- `internal/counter` (CMSketch and hybrid): identical to upstream apart from file headers.

func TestReviewProbe_LeasesBlockReader(t *testing.T) {
	e := newEngine(t, memstore.New(), func(c *taskqueue.Config) {
		c.GetTasksBatchSize, c.GetTasksReloadAt = 50, 10
		c.LongPollExpirationInterval = 11 * time.Second
	})
	for i := 0; i < 200; i++ { add(t, e, task("x")) }
	var held []*taskqueue.Delivery
	for i := 0; i < 120; i++ {
		ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
		d, err := e.PollTask(ctx, q, taskqueue.PollOptions{}); cancel()
		if err != nil { break }
		held = append(held, d)
	}
	if len(held) < 120 { t.Errorf("only %d of 120 polls got tasks though 200 are backlogged", len(held)) }
}
// Output: poll 50 failed after 50 held deliveries: no tasks; LoadedTasks:50 Backlog:200

func TestReviewProbe_DuplicateDelivery(t *testing.T) {
	e := newEngine(t, memstore.New(), func(c *taskqueue.Config) {
		c.GetTasksBatchSize, c.GetTasksReloadAt = 50, 10
		c.DeliveryLeaseDuration = 10 * time.Minute
	})
	for i := 0; i < 5; i++ { add(t, e, fairTask("A", 0.01, "a")) }
	heldA := map[int64]bool{}
	for i := 0; i < 5; i++ { d, _ := poll(); heldA[d.TaskID] = true } // hold, never ack
	for i := 0; i < 60; i++ { add(t, e, fairTask("B", 1, "b")) }
	for i := 0; i < 80; i++ {
		d, err := poll(); if err != nil { break }
		if heldA[d.TaskID] { t.Logf("DUPLICATE %d", d.TaskID); continue }
		_ = d.Ack()
	}
}
// Output: DUPLICATE: task 1..5 delivered again while its first lease is held
